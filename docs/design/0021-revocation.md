# 0021 —— 吊销只有本地那一半，缺的是分发与已装

> `draft`。这一份回答的不是"怎么加一个功能"，是"这条信任链断在哪一节"。

## 1. 问题

先纠正一句写在 [`AGENTS.md`](../../AGENTS.md) §8.3 里的话：**平台已经有吊销了**，只是只有一半。

`state.json` 的 `blockedKeys` 是一份按钥匙的公钥黑名单，`planInstall` 把它排在**第一道闸**
（`runtime/catalogue.ts` 的注释写着为什么必须排第一：排到"换人了"后面的话，一把被拉黑的
旧钥匙只要换成新钥匙，卡片就会给他一个"信任新钥匙并安装"的按钮）。命中的包连确认都不给，
界面上能看到名单、能加能删。设计是对的 —— 它绕开了"谁来签"这个问题，因为名单在本地。

它缺的是另外三件：

1. **要求用户先知道。** 钥匙泄露这件事只有作者知道，作者没有渠道说，说了用户也不一定看见。
2. **只挡安装。** `isBlockedKey` 只出现在 `installFromCatalogue` 这条路上 —— 已经装上的组件
   照跑。用户拉黑一个人之后，他桌面上那个组件还在，界面上没有任何东西说这件事。
3. **没有时效。** 包没有有效期、没有时间戳，两年前的包今天照样验得过；"回滚到旧版本"
   在密码学层看不出来。

具体的坏法：作者私钥泄露 → 攻击者用偷来的钥匙签一个 v9 推到源上 → 订阅那个源的用户点更新
→ **四道闸全过**（签名合法、钥匙和第一次装的一模一样、版本更高）→ 装进去。用户看到的是
"更新成功"。

## 2. 候选

| | A：签名过的吊销清单 | B：短时效签名 + 只往高版本装 | C：维持本地手动（现状） |
| --- | --- | --- | --- |
| 做法 | 每个源附一份 `revoked.json`（带自己的签名、单调 `version`），命中就拦新装 + 给已装的挂横幅 | 签名带 `expiresAt`，过期即拒；`publishedAt` 只当提示 | 什么都不做 |
| 换掉什么 | 换掉"用户得自己知道"这一条 —— 把知情权从用户挪回作者/源 | 换掉"签名永远有效"这个前提 | 无 |
| 新增什么 | 一份要签的清单、一个单调计数器、一条"已装但已吊销"的界面状态 | 发布流程要定期重签，否则全世界的包同时过期 | 无 |
| 代价 | **"谁来签这份清单"这个问题被请回来**（见 §3） | 作者必须周期性重签；断网久了会误判；`publishedAt` 可改，防不了降级 | 泄露之后只能等用户自己发现 |

B 单独用不成立：`publishedAt` 写在目录里，而目录不签名（[`AGENTS`](../../AGENTS.md) 不变量 15）——
改目录的人可以顺手改日期。要它成立，得先有 A 那种"另一份签过的东西"，于是又回到 A。

## 3. 决定

**A，但只做到"源运营者签自己那一份"。** 并且明确它挡不住什么。

三个"谁来签"的选项，逐个否掉两个半：

| 签发方 | 结果 |
| --- | --- |
| 组件作者自己 | 等于让被偷钥匙的人自己宣布"我的钥匙被偷了" —— 攻击者手里有同一把钥匙，他能签一份空清单盖掉它 |
| 平台更新那把钥匙 | 平台变成签发方。可这个项目**没有"平台方"**：没有服务端、没有账号、没有主体。今天那把钥匙只用来签"新版本安装包"，让它去判断"哪个第三方作者该被吊销"，是给它一个它没有的能力 |
| 每个源各自签 | 源运营者成为签发方。多源之后（[0010](./0010-multi-source-catalogue.md)）每个源各有一份 —— 这是唯一在**当前结构下**说得通的答案 |

代价要写清楚，因为它不是工程代价：

- **它挡不住源运营者作恶。** 源运营者既能签包也能签吊销，等于自己给自己发通行证。
  A 能挡的只有一种情况：**源运营者发现自己的源里有一把钥匙被偷了**，并且愿意告诉订阅者。
- **多源之后会出现"这个源说吊销、那个源没说"的分歧。** 处理方式只能是最严格的赢
  （任何一份清单命中就拦），而这会让一个恶意源拥有"吊销任何人"的权力 —— 代价是
  **可用性**，不是安全性。这个不对称是有意的：拦错了用户能手动放行，装错了收不回来。
- 工程上很小：一份静态文件、一个单调计数器、一条合并规则。**难的是治理，而治理这一版没有。**

**什么时候该推翻它**：如果第三方生态最终是"少量可信源"，A 够用；如果变成"人人都能发、
谁都能开一个源"，A 会退化成装饰 —— 那时该考虑的就不是吊销清单，而是"源本身的信誉"
（而那需要服务端，`ROADMAP` 已经明确不排）。

## 4. 接口与数据

**落盘**（和 `catalogue-cache` 同一个命名法，一个源一份）：

```
%APPDATA%\com.iron-tom.lattice\revoked\<sha256(sourceUrl)[..16]>.json
{ "schema": 1, "source": "<url>", "at": "<iso>", "version": 7,
  "entries": [{ "key": "<64 hex>", "widgetId": "a.b", "at": "<iso>", "reason": "key leaked" }],
  "publisher": { "key": "<64 hex>" }, "sig": "<ed25519>" }
```

- **清单自己要被签名**，验签用的是这个源的 `publisher.key`。取不到、验不过、`version`
  比本地那份小 —— 三种情况一律**保留本地那份**，只把"清单是 X 天前的"显示出来。
- **`version` 单调**是这份东西唯一的安全属性：没有它，攻击者拿一份旧的空清单就能把吊销抹掉。
- **`blockedKeys` 不动**。它是用户的话，优先级最高，而且没有"谁来签"的问题。
  合并顺序：**用户拉黑 → 吊销清单 → 钉住的钥匙 → 版本**。前两道都是"不装"，不分先后也行，
  但顺序写死能保证错误信息说的是用户最在意的那一条。

**已装的怎么办**：**不自动卸载。** 只在组件库那一行和属性面板挂一条横幅（"这把钥匙已被
源吊销"）+ 一个卸载按钮。理由和"新权限不自动授予也不禁用"同一条（[`AGENTS`](../../AGENTS.md) 不变量 15）：
静默卸载是替用户做决定，而用户桌面上的东西消失比一个红点吓人得多。

**要改的文件**：`runtime/catalogue.ts`（`PlanOptions` 加 `revokedKeys`，`blocked` 分支复用）、
`platform/catalogue.ts`（取清单、验签、缓存）、`platform/store.ts`（`revokedSeen` 记
每个源见过的最小 version）、`platform/LibraryPanel.tsx`（横幅）、
`src-tauri/src/revoke_policy.rs`（新，纯逻辑）。

## 5. 失败模式

| 症状 | 原因 | 正确行为 |
| --- | --- | --- |
| 断网时商店整页空白，用户以为应用坏了 | 吊销清单取不到被当成"源不可用" | 清单是**加速与保险**，不是真相：取不到就用本地那份，照常列组件，只标一行"清单是 3 天前的" |
| 吊销明明发了，用户那边还是能装 | 源运营者发的 `version` 比用户本地那份小（他重建过服务器） | 单调比较，小的丢弃并记日志；界面上给源运营者看"你发的 version 落后了" |
| 用户拉黑一个正在用的组件，它还在桌面上跑 | 拉黑只挡安装 | 这就是 §3 那条"不自动卸载"的代价，必须写在界面上，不能只在文档里 |
| 一个恶意源把所有人的钥匙都写进清单 | 多源合并取"最严格" | 拦错了可手动放行；但要把"这是哪个源说的"印在横幅上，否则用户不知道该怪谁 |

**手工验一次**：装一个包 → 手工在该源的缓存旁边写一份吊销清单（带上那把钥匙）→ 重启
→ 组件库那一行有横幅、点更新被拒、组件还在桌面上跑 → 删掉清单重启，横幅消失。
