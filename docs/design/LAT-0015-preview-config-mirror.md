# 浏览器预览那份配置镜像：认不得的字段照抄回去

## 1. 问题

浏览器预览（`npm run dev` 里那个 `/api/llm`）没有 Rust，所以 `scripts/dev-llm-proxy.mjs` 把 `llm.rs` 的配置读写抄了一份。它是**同一个 `assistant.json` 的第二个写者**。

原来的做法是白名单：`emptyConfig()` 造一份空配置，`parseConfig` 再**逐个字段**从文件里搬过来（`activeId` / `workspace` / `approvalMode` / `mode` / `skills` / `profiles` / `hands`）。

这个做法的坏处不是"多写几行"，是**漏一个字段的后果是静默数据丢失**：`skills` 就这么丢过一版 —— 在浏览器预览里拨一下手的开关，保存时把 `skills.enabled` 洗成空数组，桌面端下次启动看到"一份技能都没启用"。没有报错，没有日志，用户只会觉得"我明明开过"。

而且它**必然再漏**：`llm.rs` 每加一个字段（v2 → v3 加 `hands` / `workspace` / `approvalMode`，v3 → v4 加 `mode` / `skills`），这里都要有人记得同步。这条"要人跟的镜像"写在 AGENTS §8 里，等于承认它会再坏一次。

## 2. 候选

| 做法 | 为什么不行 |
| --- | --- |
| **A. 继续逐个字段搬，靠测试提醒** | 现在的样子。测试只能钉住"已经搬的那几个还在"，钉不住"下一个字段"。而且 `llm.rs` 与这里没有共享的清单，加字段的人多半不会想到浏览器预览 |
| **B. 把配置形状抽成一份两边都读的文件** | 听着最干净，但 Rust 那边的形状是 `struct` + 手写 JSON 读取（`llm_policy.rs` 不引 crate，`llm.rs` 用 serde），要让它读一份 JSON 形状文件就得先有一层"形状 → 代码"的生成，收益配不上复杂度；何况真正的家仍是 `llm.rs`，多一份形状文件只是把镜像换成第三份 |
| **C. 认得的归一化，不认得的原样带回去**（选中） | 白名单只管"我要理解哪些"，不再管"我要保住哪些"。新字段默认安全：它原样躺在文件里，Rust 照旧读得到 |

C 的代价：文件里可能留着一个**已经不用的旧字段**（Rust 不读它），它会一直跟着走。这个代价可以接受 —— 一个没人读的键不占任何人的注意力，而丢掉一个有人读的键会让用户重新配一遍。

## 3. 决定

1. `parseConfig` 搬完认得的字段之后，**把 `value` 里所有 `config` 还没有的顶层键原样赋进去**。`normalizeConfig` 只碰它认识的那几个，不认识的既不归一化也不删。
2. **不认识的字段不归一化**。这是有意的：这个中间件不懂它的语义，任何"顺手修一下"都可能把 Rust 写的值改坏（比如把一个枚举的新取值改成默认值）。看不懂就别动。
3. **认得的字段仍然逐个归一化**（坏档逐条丢、审批档落 `ask`、模式落 `internal`、技能 id 逐个校验）。"照抄"只覆盖不认识的，不覆盖认识的 —— 认识的字段是**判据**，判据只有一处。
4. **失败字符串也说同一种话**（[0014](./LAT-0014-llm-failure-codes.md)）：`describeStatus` / `describeFailure` 同样在抬头里给出 `@@llm:{code,status,detail}`，后面接英文原句。它是 Rust 的替身，不是第三种方言 —— 否则中文界面下桌面是中文、浏览器预览是英文。
5. **`hands` 的六个开关仍是白名单**（`HANDS_KEYS`）。将来加第七组手，两边都要改 —— 那不是一个"顺手带过去"能解决的问题：新的一组手意味着 Rust 那边真的有执行代码，预览里本来也跑不了。

## 4. 接口与数据

| 位置 | 变化 |
| --- | --- |
| `parseConfig(text)` | 认得的字段照旧搬 + 归一化；**其余顶层键原样保留** |
| `writeConfig(config)` | 不变（`JSON.stringify` 整份写，`.tmp` + 改名） |
| 落盘格式 | **没有新字段**。变化的是"不认识的东西会不会被删"，不是形状本身 |

**旧文件怎么迁**：不变。v1 平铺、v2 / v3、v4 的判定与之前一字不差；照抄只影响"文件里有、这个中间件不认识"的键，而旧文件里那些键本来就都是认识的。

## 5. 失败模式

| 坏法 | 用户看到什么 | 兜底 |
| --- | --- | --- |
| 将来 `llm.rs` 加一个顶层字段 | 浏览器预览里改设置再保存，字段还在 | 第 3 条：不认识的原样带回去 |
| 将来 `hands` 加第七组 | 预览里保存一次，那组的开关被洗成关 | 仍是白名单（第 5 条）；这是**已知**的、要人跟的一处 |
| 旧文件里留着一个已经废弃的键 | 无感 | 照抄它，Rust 不读 |
| 不认识的键是个对象，里面有一半字段作废 | 无感 | 不归一化（第 2 条）：看不懂就别动 |
| `parseConfig` 读到坏 JSON | 当没有配置（不写回） | 既有行为不变：一次解析失败不该永久丢 key |

## 6. 验收

- `npm run test:llm-proxy` 27 → **28 条**：`不认识的字段照抄回去，下一个新字段不用改这里` —— 种一份带 `futureThing` / `anotherOne` 的 v4，走一次"存手"，盘上两个键都还在、认得的 `hands.files` 也照旧生效。
- 同一批测试里补了抬头形状（`describeStatus(401, …)` 的第一行是 `@@llm:` + JSON，`describeFailure` 的网络那几条 `status: null`），并改掉那条"整条字符串短于 400"的旧断言 —— 现在短的是**抬头之后那句英文**。
- `npm run typecheck` 不涉及（`.mjs`）；`npm run check:docs` 干净。
- 真机那一段：浏览器预览里拨一下手的开关 → 退出 → 打开桌面应用，Assistant 区里那份技能清单还在（这一条和 0005 的真机验收一起走）。
