# 设计文档

> 放在这里的，是**还没做的事**在动手前的完整推理。写完不是终点：结论要沉到 [`../ROADMAP.md`](../ROADMAP.md) 的一行，断言要落进 `tests/` 或 `*_policy.rs`。
>
> 这一页既讲规矩，也讲怎么写 —— 如果你从没写过技术文档，从第三节「三遍法」开始读。

## 一、什么时候写

三个条件**同时**成立才值得开一份新文件：

1. 会动到**持久化格式**或**跨进程契约**（桥方法 / Tauri 命令 / 落盘的 JSON 结构）
2. 有**两种以上**说得通的方案
3. 做错了要**重做**，不是改几行

只中一条，写进 `ROADMAP` 的一行或 `AGENTS` 的配方节就够了。设计文档的成本不在写，在**以后每次改都得先读一遍**——所以宁可少写。

反过来说，下面这些**一定**要写：改 `state.json` 的 schema、加权限、改窗口行为、改组件包格式、改目录协议。这些做错了，已经装到用户机器上的东西没法回收。

## 二、放哪、叫什么

```
docs/design/0001-multi-source-catalogue.md
              ↑     ↑
              │     └─ 英文小写短横线。中文文件名在 Windows / git / 各种工具链上
              │        各有一处坑，省下这点表达力不值得
              └─ 四位编号，永不复用
```

开头四行状态头，`0000-template.md` 里有现成的：

```
status: draft | accepted | superseded
date: 2026-10-25
supersedes: 0003          （没有就删掉这一行）
code: src/runtime/catalogue.ts, src-tauri/src/store.rs
```

**只增不改。** 改主意就写新的一份，把旧的 `status` 改成 `superseded` 并指向新的编号。

理由是这两类文档的时态不同：`ROADMAP` 记**结论**（现在是什么样），`design/` 记**推理**（当时为什么这么想）。如果允许改旧文档，半年后你看到的就是一份"从来没犯过错"的记录，而它最有价值的部分——被否掉的方案、当时的顾虑——已经被悄悄删掉了。

## 三、三遍法

写不出来通常不是文笔问题，是还没想清楚。这个方法逼你把"想清楚"和"写得好"分开：

**第一遍，20 分钟，只写骨架。** 六个小标题，每个下面一句话结论。不查资料、不贴代码、不排版。写完如果发现某一段憋不出一句话，那一段就是你没想清楚的地方——回代码里去看，别硬编。

**第二遍，补证据。** 每条结论后面挂三样东西之一：
- 一个**位置**（`src/runtime/bridge.ts:412`）
- 一个**数字**（300ms、12 KB、256 块、16 次调用）
- 一个**症状**（"WebView2 把窗口切成横条"）

三样都挂不上的句子，删掉。形容词（"更优雅""性能更好""更安全"）不是证据。

**第三遍，删一半。** 两条删掉规则：
- 读代码就知道的 → 删（文档不该复述代码）
- 换个实现就失效的 → 删（那不是设计，是实现细节）

删完还剩两页以内，就对了。超过两页，说明这件事该拆成两件。

## 四、六段

顺序不能换，因为后一段依赖前一段的结论。

| # | 段 | 写什么 | 最常见的错误 |
| --- | --- | --- | --- |
| 1 | 问题 | 不做会怎样。一句话，具体到"谁在什么场景下会坏" | 写成背景介绍 / 行业综述 |
| 2 | 候选 | ≥2 个方案，各自**换掉**什么 | 只写自己想的那个，然后论证它对 |
| 3 | 决定 | 选哪个 + 代价。代价必须是真的代价 | 只写好处，代价写"暂时有点不完美" |
| 4 | 接口与数据 | 跨进程那一条：方法名、参数、落盘格式、旧数据怎么迁 | 画架构图 |
| 5 | 失败模式 | 每种失败**长什么样**（症状）+ 正确行为 | 写"要有完善的错误处理" |
| 6 | 验收 | 断言落在哪个文件、几条、钉的是哪条不变量 | 写"测试要充分" |

逐段看一个本仓库的真事，比抽象讲解有用：

| # | 范例（真实片段） |
| --- | --- |
| 1 | "目录读一次要 300ms。断网时商店是空白的，而空白会被当成'应用坏了'" |
| 2 | "A：每次全量 GET。B：`If-None-Match` + 本地缓存。C：后台轮询刷新" |
| 3 | "选 B。代价：目录才几 KB，304 省不下流量——它买的是'内容真的没变'这个证据" |
| 4 | "缓存落在 `catalogue-cache/<sha256(url)[..16]>.json`，内容 `{schema,url,at,etag,text}`" |
| 5 | "解码任何一条不合法都当'没有缓存'。缓存是加速不是真相，读坏的后果应该是照常走网络，不是界面上一堆怪报错" |
| 6 | "`tests/catalogue.html` 6 条：304 走缓存、地址变了整份作废、坏 JSON 当没有缓存" |

## 五、两段必须手写，不能省

**第 2 段（候选）** 是判断作者有没有真想过这件事的唯一凭据。只有一个方案的"设计"是宣布，不是设计。写的时候给自己定个规矩：**至少一个候选是你本来想选的**，另一个是你否掉的——把它们并列写出来，理由才立得住。

**第 5 段（失败模式）** 是这个仓库最贵的一课。三条真实教训，症状和原因长得完全不像：

- `SetWindowRgn` 之后不补 `RedrawWindow` → 宠物被切成一行一行的横条（原因：WebView2 按上一次的脏区重绘）
- release 勾了 pre-release → 更新器报"检查你的网络"，而网络完全正常（原因：`/releases/latest` 跳过预发布，404）
- 组件在等桥的 3 秒 → 卡片空白 6 秒（原因：`config.get` 和 `storage.get` 各 3 秒超时，串行）

写这一段的正确姿势：**先写"用户会看到什么"，再写"原因是什么"**。排查的人永远从症状开始，不会从原因开始。

## 六、写完之后

三件事，缺一件这份文档就等于没写：

1. **`ROADMAP` 追加一行**：`- [x] 标题 —— 一句话结论 + 代价`。不追加的话，没人会翻到 `design/`。
2. **断言落地**：纯逻辑进 `*_policy.rs`（`rustc --test` 跑得动），行为进 `tests/*.html`，尺寸进 `.scratch/` 探针。第 6 段写了几条，这里就要有几条。
3. **如果它推翻了旧决定**：把旧决定挪到 `ROADMAP` 的「被推翻的八个决定」一节，写清"原来怎么想、被什么推翻的"。那一节是这个仓库最值钱的部分。
