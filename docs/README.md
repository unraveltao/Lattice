# 文档地图

> 这一页回答三个问题：**哪份该读、哪份该改、新东西该放哪。**
> 它不是内容索引（各文件的标题已经说明内容），是**归属表**。和代码冲突时以代码为准，并顺手回来改这一页。

## 一、按你要做的事找

| 你要做的事 | 读这份 | 花多久 |
| --- | --- | --- |
| 第一次打开这个仓库 | [`../README.md`](../README.md) → [`ARCHITECTURE.md`](./ARCHITECTURE.md) | 15 分钟 |
| 写一个组件 | [`WIDGET_SPEC.md`](./WIDGET_SPEC.md) | 30 分钟 |
| 改平台代码 | [`../AGENTS.md`](../AGENTS.md)（先读第 4 节十八条不变量） | 20 分钟 |
| 加一个能力（桥方法 / 权限 / 窗口行为） | [`AGENTS.md` 第 7 节"常见改动的配方"](../AGENTS.md) + `WIDGET_SPEC` 对应章节 | 按需 |
| 想知道某个奇怪设计为什么是这样 | [`ROADMAP.md`](./ROADMAP.md)「被推翻的八个决定」 | 按需 |

## 二、每份文档的职责

| 文件 | 回答的问题 | 时态 | 什么时候改 |
| --- | --- | --- | --- |
| `README.md` / `README.zh-CN.md` | 这是什么、现在到哪一版、数字是多少 | 现在 | **每个版本** |
| `docs/ARCHITECTURE.md` | 为什么长成这样（分层、沙箱、窗口、数据） | 过去 | 架构真的变了才改 |
| `docs/WIDGET_SPEC.md` | 组件作者必须遵守的契约 | 现在 | 加桥方法 / 权限 / 清单字段 |
| `AGENTS.md` | 改代码前必须知道的不变量、缺口、配方 | 现在 | 目录结构或验证方式变了 |
| `docs/ROADMAP.md` | 走到了哪、哪些决定被现实推翻过 | 过去 | 每完成一件事**追加**一行 |
| `docs/design/` | 一件**还没做**的事，动手前怎么想 | 未来 | 只增不改，改主意就写新的 |
| `docs/AGENT_ACCESS.md` | agent 接入的协议与威胁模型 | 混合 | 只在碰 agent 时 |
| `docs/CODE_SIGNING.md` | 签名买不买、免费路线怎么走 | 定案 | 政策变了才改 |
| `docs/PET_REFERENCE.md` | 桌宠素材从哪来、许可到哪、骨骼怎么跑 | 参考 | 换素材时 |
| `docs/VELA-REUSE.md` | 邻仓 vela-cleanroom 能搬什么 | 参考 | 一次性，基本不动 |

## 三、新内容放哪

四类，判断标准不是"内容像什么"，是**"三个月后谁还会来读它"**。

| 类型 | 特征 | 放哪 |
| --- | --- | --- |
| **入口** | 第一次来的人读，随版本变 | 根 `README.md` |
| **契约** | 别人（组件作者、平台自己）必须遵守 | `docs/` 根，一份，不拆 |
| **决策** | 有替代方案、有代价、事后要能查 | `docs/ROADMAP.md` 一行 + `docs/design/` 一篇 |
| **参考** | 一次性，不会有人反复读 | `docs/reference/`（还没建，第二份参考进来时建） |

三个问题定去向，从上往下问，命中就停：

1. **三个月后还有人要照着它做吗？** 没有 → 参考。
2. **它有没有被否掉的替代方案？** 有 → 决策。结论写进 ROADMAP 一行，推理进 `design/`。
3. **它是别人必须遵守的吗？** 是 → 契约，进 `docs/` 根。

三个都不命中 → 它大概不该是文档，是代码注释或 `AGENTS.md` 配方节里的一行。

**反例，别做**：不要新建 `总览.md` / `说明.md` / `开发文档.md`。这类文件名说明作者还没想清楚它属于哪一类，而它一旦存在，就会变成第三个"事实的家"。

## 四、一份事实只有一个家

重复是文档腐烂的起点：两处写着同一件事，改了一处，另一处就开始骗人。

| 事实 | 家 | 别处怎么提 |
| --- | --- | --- |
| 桥方法表、参数校验、权限闸门 | `src/runtime/bridge.ts` | 文档写"有什么、为什么"，**不抄签名** |
| 权限清单 | `src/runtime/catalogue.ts` 的 `KNOWN_PERMISSIONS` | `WIDGET_SPEC` 写语义，不写代码 |
| 组件作者契约 | `docs/WIDGET_SPEC.md` | 别处给链接 |
| 改代码的约束 | `AGENTS.md` | 别处不重复 |
| 决定与代价 | `docs/ROADMAP.md` | `design/` 只写推理，结论链接过去 |

判断方法：**这段内容如果代码改了要不要跟着改？** 要 → 它不是文档，是指针，改成链接。

## 五、发版时要同步哪三处

这三处最容易过期，而且过期了不会报错：

1. `README.md` 的 **By the numbers**（组件数 / 权限数 / 断言数 / 文档坑数）—— 数字变了要重数一遍，别估。
2. `ROADMAP.md` 的**进度总览**表 —— 一条版本从"进行中"变"已完成"。
3. `AGENTS.md` 的**已知缺口**表 —— 补掉一条就删一条，别留着当"历史"。

## 六、别做的事

- **别为了完整复制代码。** 抄过来的那一刻就开始过期。
- **别把一个决定写在三份文档里。** 结论在 ROADMAP，推理在 design，约束在 AGENTS —— 各写各的那一半。
- **别在规范里写教程。** `WIDGET_SPEC` 回答"必须怎样"，不回答"我该从哪学起"；后者是 `README` 和 `examples/` 的活。
- **别删旧文档。** 错了就标 `superseded` 并指向新的。这个仓库的价值有一半在"知道哪些路走不通"。
