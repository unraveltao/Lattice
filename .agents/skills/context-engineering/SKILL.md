# 上下文工程

这一轮能花的注意力是有限的；仓库是无限的。做错这件事的代价不是报错，是**慢、贵、然后在关键处忘掉一条不变量**。

## 0. 三个判据

- **对话是临时记忆，文件是长期记忆。** 这一轮想明白的事，不落盘就等于没发生：下一轮（或下一个会话、或压缩后的自己）从零开始。
- **读进来的是成本，带出去的是价值。** 每读一份文件都要能回答"我下一步动作会因为这份内容改变什么"；答不上来就是白读。
- **地图先于地形。** 先看"有哪些文件、各自管什么"，再决定读哪一份的哪一段。这个仓库的地图是 `docs/README.md`，约束是不变量，工序是 `.agents/skills/`。

## 1. 读之前：先定位，再取一段

```bash
# 不要上来就 read 整份
grep -n "要搜的东西" src/xxx.ts     # 拿到行号
```

然后 `read` 带 `offset` / `limit`，只取那一段 ±40 行。`src/styles.css` 有五千多行、`AGENTS.md` 七百多行 —— 整份读一遍花掉的是后面改代码的预算。

| 想读 | 先这样 |
| --- | --- |
| 某个符号在哪、被谁用 | `grep` 符号名，看命中的行号与文件分布 |
| 某个能力现在做到哪 | `AGENTS.md` 第 8 节缺口表 + `ROADMAP` 进度表（各读几十行） |
| 某段历史为什么这样 | `git log --oneline -8 -- <path>`，比翻 `history.md` 快 |
| 某个词的意思 | `GLOSSARY.md` 搜一行 |

## 2. 读进来之后：短的进结论，长的进文件

- **结论落盘**：算出来的数字、定下的名字、否掉的方案 → 写进 `docs/` 一行或提交说明，别只活在对话里。
- **过程不进 `docs/`**：一次性的调试路径是"这次怎么撞出来的"，那属于提交说明和 `PITFALLS` 的一条，不属于设计稿。
- **别重复**：同一句话在对话里说第二遍就是在花预算买同一件东西 —— 删掉，指向上一次落盘的位置。

## 3. 工具输出：只要结论那几行

- 跑构建 / 测试：`Select-Object -Last N`（或 `tail -n`），别把几千行塞回上下文。
- 列文件：`glob` 拿路径，不要 `Get-ChildItem -Recurse` 的整棵树。
- 网络 / API：只取需要的字段，别 `ConvertTo-Json` 一份两万字的响应。
- 长输出要留证据时，把它写进 `.scratch/<名字>.log`，上下文里只留"路径 + 最后几行"。

## 4. 分工：什么该由 skill / 文档 / 代码分别记住

- **skill**：工序（先做什么、按什么顺序）。只在任务命中时加载 —— 别为了"熟悉一下"把七份全读一遍。
- **文档**：事实与判据（约束、决定、坑、词）。
- **代码**：最终依据。文档和代码冲突时以代码为准，并顺手改文档。

## 5. 压缩 / 换会话之后

先重建这四样，再动手（顺序别换）：

1. 当前目标（要交什么、done-when 是什么）；
2. 已经改了哪些文件、有没有未提交的别人的改动（`git status --short`）；
3. 门禁状态（`typecheck` / `check:docs` / 相关断言页最近一次是绿是红）；
4. 下一步那**一个**动作。

**别重读一遍全部文档来"恢复记忆"** —— 那会把刚省下的预算再花一遍。

## 6. 反例

| 看着合理 | 实际代价 | 换成 |
| --- | --- | --- |
| 每次改完都跑全量 `test:browser`（51 页） | 几分钟 + 几十屏输出 | `--filter <相关页>`，交付前再跑全量 |
| 为理解界面整份读 `styles.css` | 五千行换一行结论 | `grep` 类名，读那一块 |
| 把 100 行测试输出贴进对话 | 后面忘掉不变量 | 只留 `FAIL` 行与汇总那一行 |
| 在对话里复述刚读到的设计 | 同一件事说两遍 | 一句话 + 文件路径 |
